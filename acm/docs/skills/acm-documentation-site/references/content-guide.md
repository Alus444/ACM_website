# 公開本文の組み方

## 情報を分ける

仕様書や完全解説書に含まれる情報を、そのまま公開ページの目次へ変換しない。

- 一般ユーザー向け本文: 何ができるか、導入方法、使い方、設定の意味、困ったときの対処。
- 必要な場合だけ別ページ: 利用規約、リリース情報、既知の問題、対応環境。
- 公開本文から分離: 実装・ビルド情報、内部試験記録、デバッグ手順、開発用の再現条件、保守者向け識別子。
- 互換性や確認済みバージョンは、根拠のある表現だけを使う。「対応」と「動作確認済み」を混同しない。
- 版数、配布方法、UI英語名、範囲、初期値などが未確認なら、公開本文へ`0.0.0`や仮の数値を置かない。[source-verification.template.md](../assets/source-verification.template.md)を作業用に複製し、確認待ちの事実を本文と分離する。

## ページを作る基準

- 読者の目的が独立しているときだけページを分ける。
- 内容がほぼ同じ項目は統合する。ページ名だけ違う重複を作らない。
- 「詳細を見る」の遷移先は、遷移前より具体的な説明、範囲、例、注意点のいずれかを増やす。情報量が増えないならリンクを置かない。
- プリセット名だけ、手順名だけ、機材用語だけの一覧にしない。見た目、向く素材、判断基準を添える。
- 調整レシピは再現性と用途がある場合だけ作る。

## 日本語

- UI名や専門用語の直後に、映像・操作・結果がどう変わるかを書く。
- CRT、TVL、RF、AWBなど初見で分かりにくい語が複数ある場合は用語集を用意する。
- 用語集は辞書的な定義より、画面上の見た目や操作との関係を優先する。
- 「このサイトでいう」「〜に絞って説明します」「まず見る」「まず触る」「まずここ」といった説明者都合・プロンプト調の言い回しを避ける。
- 「最短手順」「調整順の基本」のような一般論は、読者がそのまま操作できる具体性がなければ置かない。
- チェックボックス記号を装飾として使わない。本当に完了状態を操作・記録するUIだけに使う。
- 手順番号は`1 / 2 / 3`とし、装飾目的の`01 / 02 / 03`にしない。
- 見出しは読者が探す語にする。本文は結論または見た目の変化から始める。

## パラメータ説明

各パラメータは、別項目を増やさず次の順序を1つの説明単位にまとめる。

1. 日本語名と実UI上の英語名。
2. 何を変える設定か。値を増減したとき見た目がどう動くか。
3. 範囲と初期値。初期値はバーや選択肢の近くに表示する。
4. 調整の目安。説明文の後ろに続け、独立カードを乱造しない。
5. 混同しやすい別設定がある場合だけ、その違い。

範囲表示は操作できそうなinputスライダーに見せない。非操作のメーターとして表示し、初期値マーカーと数値を同じ視線範囲に置く。

## ページ構成の例

必要なものだけ選ぶ。製品ごとにこの順序を強制しない。

- 概要・対応環境
- インストール／更新／削除
- 代表的な使い方または内蔵プリセット
- 画面構成または機能別リファレンス
- 全項目早見表
- 用語集
- 想定される問題／トラブル対応
- リリース情報
- 利用規約

トップの概要ページは、製品の役割、代表的な結果、対応状況、主要導線を短く示す。全機能を詰め込まない。
